## 6.5 Domain classes to components

## 6.6 Design principles applied

| Principle | Where it shows in our design | Evidence (component, interface, ADR) |
|---|---|---|
| Separation of concerns | Collecting events, storing them, showing them and building a calendar file are four separate jobs, each in its own component. | 6.3: C1 Event Collector, C2 Event Storage, C3 Website, C4 Calendar Download |
| Information hiding | Only the collector knows how UTD Calendar and Nebula format their pages. The website never touches a source site and only sees one shared event format. | 6.3: only C1 connects to R1 and R2. 6.4: C3 reads the deployed `events.json` only |
| Low coupling | The components talk through one file. The collector writes `events.json`; the website and calendar function read it. If a source site changes its layout, only C1 needs a change. | 6.4: C1 pushes `events.json` to the repository, which triggers a Vercel redeploy. [ADR-01] |
| High cohesion | Each component does one thing. C4 only turns one chosen event into an `.ics` file. C3 only displays and filters events. | 6.3: C4 takes "chosen event" and "event details" and returns a `.ics` file |
| Design for change | A third event source would be a new reader inside C1 with nothing else changing. The refresh interval and the hosting provider are recorded as decisions. | [ADR-02], [ADR-03] |
| Keep it simple (KISS) | No accounts, no database server and no user-created events. One background job, one JSON file and a static website on free hosting. | 6.4: Vercel Hobby plan and the GitHub Actions runner. README scope: no user accounts, direct event creation or comments |
